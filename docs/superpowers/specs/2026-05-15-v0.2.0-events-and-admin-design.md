# sinpapel-webhooks v0.2.0 — Event catalog expansion + Admin REST API

**Date:** 2026-05-15
**Status:** Draft — pending implementation plan
**Author:** brainstorming session
**Bumps:** 0.1.1 → 0.2.0 (MINOR, additive non-breaking)

## 1. Context

`sinpapel-webhooks` v0.1.1 ships with three event types
(`workflow.transition.completed`, `signature.completed`, `document.uploaded`)
and a single inbound endpoint (`POST /in/<source>/`). It does NOT expose
admin/management endpoints — subscription CRUD was deferred (S14.5).

In parallel, `sinpapel` advanced to v0.4.0 adding five capabilities not yet
representable as webhook events:

1. **Transition Predicates** (`CondicionTransicion` + `PredicateEngine`)
2. **Structured Metadata Capture** (`MetadatosCapturables` + `MetadatosProxy`)
3. **Form/Serializer Factory** (`MetaFormFactory`) — config-time, no runtime event
4. **State Timers / SLA** (`SLAConfiguracion` + `SLAEngine` + `sinpapel_verificar_slas`)
5. **Preview Transition** (`WorkflowEngine.preview_transition`)

This spec closes both gaps: a new event catalog covering the five features
above, and the deferred admin REST API (S14.5).

## 2. Goals

- Emit webhook events for the new sinpapel capabilities while preserving the
  loose-coupling rule (sinpapel core MUST NOT import sinpapel-webhooks).
- Provide an admin REST API for Subscriptions (CRUD), Deliveries (read +
  retry/requeue), Events (read), InboundEvents (read).
- Keep the new API surface optional — DRF stays a soft dependency.

### Non-goals

- Multi-tenancy of subscriptions.
- Pluggable signing algorithms (HMAC-SHA256 stays the only signer).
- Rate limiting on admin endpoints (left to consumer's middleware).
- Replacing the inbound receiver framework — `/in/<source>/` is untouched.

## 3. Event Catalog Additions

| event_type | Trigger | Coupling | Payload keys |
|---|---|---|---|
| `workflow.predicate.failed` | sinpapel Signal `predicate_failed` fired from `WorkflowEngine._validar_predicados` when a `CondicionTransicion` rejects a transition. | Loose (signal) | `condicion_id`, `tipo`, `mensaje_error`, `transicion_id`, `target_object_id`, `target_content_type`, `target_state`, `user_id` |
| `workflow.predicate.configured` | Django `post_save` of `CondicionTransicion`. | Auto (signals.py) | `condicion_id`, `transicion_id`, `tipo`, `configuracion`, `mensaje_error`, `orden`, `activo`, `action` ("created" or "updated") |
| `workflow.transition.preview` | sinpapel Signal `transition_preview_requested` fired at the end of `WorkflowEngine.preview_transition`. Opt-in via setting `SINPAPEL_EMIT_PREVIEW_EVENTS=True` (default `False` to avoid noise). | Loose (signal) | `target_object_id`, `target_content_type`, `target_state`, `user_id`, `permitido`, `razones_bloqueo`, `side_effects`, `documentos_faltantes`, `predicados_fallidos` |
| `sla.configured` | Django `post_save` of `SLAConfiguracion`. | Auto (signals.py) | `sla_id`, `estado_id`, `dias_maximos`, `accion_vencimiento`, `configuracion_accion`, `activo`, `action` |
| `sla.breached` | sinpapel Signal `sla_breached` fired from `SLAEngine._sla_vencida` when an instance exceeds `dias_maximos`. | Loose (signal) | `sla_id`, `estado`, `dias_maximos`, `dias_transcurridos`, `target_object_id`, `target_content_type` |
| `sla.action.executed` | sinpapel Signal `sla_action_executed` fired from `SLAEngine._ejecutar_accion` after dispatching `_accion_*` handler. | Loose (signal) | `sla_id`, `accion` (notificar/escalar/rechazar/alertar), `configuracion_accion`, `resultado`, `target_object_id`, `target_content_type` |
| `workflow.metadata.captured` | OPT-IN per consumer model: consumer calls `emit_event("workflow.metadata.captured", payload, source=instance)` explicitly from its own `post_save` handler. NOT auto-emitted on the abstract mixin (would be too broad). | Consumer-emit | `target_object_id`, `target_content_type`, `schema_fields` (list of field names), `datos_capturados` (dict from `meta.to_dict()`) |

### Custom signals declared in sinpapel

A new module `sinpapel/signals.py` declares Django Signals only (NO import of
sinpapel-webhooks):

```python
# sinpapel/signals.py
from django.dispatch import Signal

predicate_failed = Signal()                # kwargs: target, condicion, user, target_state
sla_breached = Signal()                    # kwargs: target, sla, dias_transcurridos
sla_action_executed = Signal()             # kwargs: target, sla, accion, resultado
transition_preview_requested = Signal()    # kwargs: target, target_state, user, reporte
```

`WorkflowEngine` and `SLAEngine` fire these via `signal.send_robust(sender=type(target), ...)`
so that downstream errors never poison the workflow path. If
`SINPAPEL_EMIT_PREVIEW_EVENTS` is not truthy, `preview_transition` skips the
`transition_preview_requested` send entirely.

### Receivers registered in sinpapel-webhooks

`sinpapel_webhooks/signals.py` adds receivers connected at `apps.ready()` time
behind a defensive import:

```python
try:
    from sinpapel.signals import predicate_failed, sla_breached, sla_action_executed, transition_preview_requested
except ImportError:
    pass  # sinpapel version too old, skip new events
else:
    predicate_failed.connect(on_predicate_failed)
    sla_breached.connect(on_sla_breached)
    sla_action_executed.connect(on_sla_action_executed)
    transition_preview_requested.connect(on_transition_preview_requested)
```

Each handler builds a snapshot payload synchronously and defers
`emit_event(...)` inside `transaction.on_commit` to match the pattern of
existing handlers in `signals.py`.

### Source GFK behavior

`emit_event(source=...)` keeps the existing GFK semantics:
- For `*.configured` events, `source` is the `CondicionTransicion` or
  `SLAConfiguracion` row.
- For `*.failed`, `*.breached`, `*.action.executed` events, `source` is the
  business target (the model instance being transitioned/timed), so the admin
  linkback points to the affected entity, not the configuration row.
- For `*.preview`, `source` is the target instance (audit linkback).

## 4. Admin REST API

### 4.1 Packaging

- New subpackage: `sinpapel_webhooks/admin_api/` with `viewsets.py`,
  `serializers.py`, `permissions.py`, `urls.py`.
- Optional install extra: `pip install sinpapel-webhooks[admin]` which pulls
  `djangorestframework>=3.14`.
- `sinpapel_webhooks/urls.py` mounts the admin include behind a defensive
  `try/except ImportError`. If DRF is absent at runtime, only `/in/<source>/`
  is exposed.

### 4.2 URL mount

Consumer wires it the same way as the inbound endpoint:

```python
# mossc/urls.py
urlpatterns = [
    path("sinpapel/api/webhooks/", include("sinpapel_webhooks.urls")),
]
```

`sinpapel_webhooks.urls` then includes:

- `path("in/<source>/", InboundWebhookView.as_view(), ...)` (existing)
- `path("admin/", include("sinpapel_webhooks.admin_api.urls"))` (new, gated by DRF availability)

### 4.3 Endpoint inventory

```
Subscriptions
  GET    /admin/subscriptions/                       paginated list
  POST   /admin/subscriptions/                       create — response body returns `secret` ONCE
  GET    /admin/subscriptions/{id}/                  retrieve — secret masked as "***" + last 4 chars
  PATCH  /admin/subscriptions/{id}/                  partial update (cannot rotate secret here)
  DELETE /admin/subscriptions/{id}/                  hard delete
  POST   /admin/subscriptions/{id}/rotate-secret/    response body returns new secret ONCE
  POST   /admin/subscriptions/{id}/test/             enqueue synthetic delivery (uses existing test command logic)

Deliveries
  GET    /admin/deliveries/                          filterable list (`?status=`, `?subscription=`, `?since=`)
  GET    /admin/deliveries/{id}/                     retrieve
  POST   /admin/deliveries/{id}/retry/               re-enqueue a single delivery (force regardless of status)
  POST   /admin/deliveries/requeue-dead-letter/      body `{ids: [...]}` or `{all: true}`; returns count

Events
  GET    /admin/events/                              filterable list (`?event_type=`, `?since=`)
  GET    /admin/events/{id}/                         retrieve, embeds related deliveries (slim)

Inbound Events
  GET    /admin/inbound-events/                      filterable list (`?source=`, `?handler_status=`, `?since=`)
  GET    /admin/inbound-events/{id}/                 retrieve
```

### 4.4 Auth + permissions

- Default permission class: `IsAdminUser`.
- Override via setting:
  ```python
  SINPAPEL_WEBHOOKS_ADMIN_PERMISSION = "myapp.permissions.IsOpsTeam"
  ```
  Resolved at module import using Django's `import_string`. A missing or
  unimportable path raises `ImproperlyConfigured` at startup.
- DRF auth: defaults to `DEFAULT_AUTHENTICATION_CLASSES` from project settings
  (Session + Token typical). No webhook-specific auth configured.

### 4.5 Serializers

- `WebhookSubscriptionSerializer`:
  - On create response: `secret` field is full value (only time it's visible).
  - On retrieve/list: `secret` field is masked (`"***" + last 4`).
  - On update: `secret` is read-only (must go through rotate endpoint).
- `WebhookDeliverySerializer`: read-only fields, includes nested
  `subscription.name` + `event.event_type` for list ergonomics.
- `WebhookEventSerializer`: read-only. List view includes `delivery_count` only;
  retrieve view embeds a `deliveries` array with `[{id, subscription_id, status, attempts, last_response_status}]` per delivery.
- `InboundWebhookEventSerializer`: read-only.

### 4.6 Pagination + filtering

- Default pagination: `PageNumberPagination` with `page_size=50`,
  overridable via `SINPAPEL_WEBHOOKS_ADMIN_PAGE_SIZE`.
- Filtering: `django-filter` if available (soft dep), else simple
  `filter_queryset` overrides reading `request.query_params`.
- Ordering: default `-created_at` (or `-occurred_at` / `-received_at`).

### 4.7 OpenAPI schema

If `drf-spectacular` is installed, schema is auto-generated under
`GET /admin/schema/`. Otherwise the route is simply not wired (consumer
without `drf-spectacular` does not get an OpenAPI doc — README documents the
API). No static fallback fixture (YAGNI).

## 5. Loose-coupling guarantees

- `sinpapel/signals.py` only imports `django.dispatch`. No sinpapel-webhooks
  imports in any sinpapel module.
- `sinpapel_webhooks/signals.py` defensively imports from `sinpapel.signals`;
  catches `ImportError` so the package works against older sinpapel pinned
  versions.
- `admin_api/` defensively imports DRF; catches `ImportError` so the package
  works without the `[admin]` extra installed.
- `pyproject.toml` keeps `sinpapel` and `djangorestframework` as soft deps in
  the relevant extras; no version pin tightening on existing extras.

## 6. Settings additions

```python
# Existing (unchanged):
SINPAPEL_WEBHOOKS_INBOUND_SECRETS = {"baz": "..."}
SINPAPEL_WEBHOOKS_TIMESTAMP_TOLERANCE = 300
SINPAPEL_WEBHOOKS_DELIVERY_BACKEND = "inline"  # / "outbox" / "celery"
SINPAPEL_WEBHOOKS_DEAD_LETTER_AFTER_ATTEMPTS = True

# New:
SINPAPEL_WEBHOOKS_ADMIN_PERMISSION = "rest_framework.permissions.IsAdminUser"
SINPAPEL_WEBHOOKS_ADMIN_PAGE_SIZE = 50
SINPAPEL_EMIT_PREVIEW_EVENTS = False  # sinpapel-side toggle for transition.preview event
```

The `SINPAPEL_EMIT_PREVIEW_EVENTS` toggle lives on the sinpapel side because
the producer is `WorkflowEngine.preview_transition`. sinpapel-webhooks doesn't
need to read it.

## 7. Testing strategy

- 1 unit test per new event in `tests/test_signals_events.py`:
  - emits the signal / saves the model.
  - asserts a `WebhookEvent` row is created with the expected payload keys.
  - asserts a `WebhookDelivery` row is created for a matching active
    subscription.
- 1 smoke test per admin endpoint in `tests/admin_api/` covering:
  - happy path (200 with correct shape).
  - permission denial (403 without admin).
  - filter parameter (where applicable).
- Cross-component E2E (extend existing `test_cross_component_e2e.py`):
  HMAC roundtrip for one of the new event types end to end.

Coverage target: maintain ≥99% (current baseline).

## 8. Migration path

- No DB migrations required (no model changes; existing tables suffice).
- README updates: add "Event catalog v0.2.0" section + "Admin API" section
  with `curl` examples.
- CHANGELOG: new `[0.2.0]` block under "Added" listing all events + admin
  endpoints.

## 9. Risks + mitigations

- **Risk:** Signal storms if a consumer rapidly fires many predicate failures
  or SLA breaches.
  - **Mitigation:** All emissions go through the existing outbox/Celery
    backend; no inline storms unless backend is `inline`. Documented in
    README.
- **Risk:** Admin endpoints leaking subscription secrets if mis-permissioned.
  - **Mitigation:** Default `IsAdminUser`, secret masking on read, secret
    write-only via dedicated rotate endpoint, secret never persisted in
    response logs (DRF default).
- **Risk:** drf-spectacular not installed → schema endpoint 500s.
  - **Mitigation:** Static fallback schema + try/except detection at URL
    wiring time.
- **Risk:** sinpapel `Signal()` not present in older versions.
  - **Mitigation:** Defensive import in `sinpapel_webhooks/signals.py`. CI
    tests against both `sinpapel>=0.4` and one prior minor.

## 10. Out of scope (parking lot)

- Multi-tenant subscription isolation.
- Webhook replay UI.
- Subscription-scoped event filters beyond JSONField `__contains` (e.g.,
  payload predicates).
- Signing algorithm pluggability.
- Rate limiting on admin endpoints.

## 11. Acceptance criteria

- `sinpapel-webhooks` exposes 10 event types (3 existing + 7 new) end to end
  through outbox + Celery + inline backends.
- Admin REST API covers all routes in §4.3 with auth gating, secret masking,
  and pagination working.
- Suite is green with ≥99% coverage and at least one new cross-component E2E
  test passing.
- README + CHANGELOG updated. Package builds with `pip install
  sinpapel-webhooks[admin]`.
